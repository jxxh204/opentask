Docs

How to install OpenTask, how each feature actually works, and what to watch out for.

Overview

OpenTask is a parallel dev control tower: add a subtask under a task and it gets its own isolated git worktree plus an AI coding agent (Claude Code, etc.). The goal is to keep the loop — create a task → subtask (worktree) → agent wave → calendar sync — alive in one place, without bouncing between terminal tabs.

It started as a tool for a single operator, and broadened as it went open source: several people now use it together to watch and direct agents across many worktrees at once, as a small dev team.

Two ways to run it. ① Dev mode, launched straight from source (a Vite dev server plus a separate Node backend process). ② The packaged macOS Electron desktop app. Both run the exact same frontend/backend code with no feature difference — Electron is just the distribution format, not a separate feature set. In the packaged app the backend runs as its own detached process, so quitting the app window entirely (Cmd+Q) doesn't kill an agent session that's still working.

Quickstart

Grab the signed app from the download page, or get it running from source in three steps.

git clone https://github.com/jxxh204/opentask cd opentask/app npm install npm run electron:dev

When the command finishes, the OpenTask desktop window opens. With nothing configured yet, you get demo data so you can explore the whole screen layout (task tree · calendar · cron jobs · assistant) right away. To connect your real repo, hit "Add Repo" on the onboarding screen — see Install and Creating a Task for the full walkthrough.

Just want to look around faster? Run npm run start instead of npm run electron:dev and open http://localhost:5180 in your browser to see the same screen without a desktop window.

Want to see it again later? Open the sidebar "Settings" → "Show quickstart again" any time.

Install

Option A · Download the app

A macOS app signed with an Apple Developer ID (not yet notarized) is available right now on the download page.

Option B · Build from source (available right now)

Clone the repository and run it from the app/ folder.

git clone https://github.com/jxxh204/opentask cd opentask/app npm install npm run start # backend (8770) + frontend (5180) together

To launch it straight as a desktop window (Electron):

npm run electron:dev

On first launch you connect a repo from the onboarding screen. You can also explore the layout first with demo data before connecting anything.

Troubleshooting — native module build errors

better-sqlite3 and node-pty are native modules, so a Node/Electron version bump may require rebuilding them.

# Rebuild for Node (plain npm run start / npm run server) npm run rebuild:node # Rebuild for Electron (electron:dev / electron:build) npm run electron:rebuild

Core Concepts

Tasks and subtasks

A task (a "main task," really a "folder" under the hood) is a unit that groups work. Subtasks created under it each get mapped to an isolated git worktree with a real tmux/Claude Code terminal session. All actual code work happens only inside those per-subtask worktrees — the main task itself only handles orchestration.

Task Manager · waves

The Task Manager (orchestrator) has no separate "start" button — the instant a subtask is created under a task, it automatically takes control and drives subtasks one at a time in sequential "waves." Alongside the live terminal, you can see the plan · dispatch · report · message · error log the conductor keeps for itself, organized as a structured tree.

v1 limitation. Wave progress state lives in memory — it's lost if the app (server) restarts.

Diagram (assembly-line board)

A board that summarizes a task's subtask chain left-to-right, like an assembly line. Each card shows a subtask's status — waiting, in progress, or session ended — along with its scheduled duration.

Calendar · blocked periods

Place subtasks' due dates on a week/month calendar and drag to reschedule. Stretches where work shouldn't happen — a QA freeze, say — are marked as blocked periods and shown as stripes on the calendar (they don't actually prevent scheduling).

Team Rules

Instead of hardcoding one team's conventions (branch naming, commit format, required pre-docs, etc.) into the app, you register them as free text per repo, and that text is carried straight into every agent's instructions. OpenTask's code never parses this text — "following" it is entirely up to the agent reading those instructions, using the shell/MCP tools it already has.

Model Policy

Assign which AI model to use for each of 16+ task types — design, Task Manager, control, coding, review, QA, and more — as a policy.

Assistant

A top-level agent that runs the whole app by conversation — not a single task, but the calendar, cron jobs, and operational settings together. It's deliberately kept separate (name and place) from the Task Manager: this one directs "the whole app," not "this task."

A live connection — Calendar & Cron Jobs

Drag a subtask on the calendar and its real due date actually changes. A cron job fires at its scheduled time and a genuinely new task gets created — not just a log line saying it would have.

How to Use — Creating a Task

  1. Click "Add Task" above the sidebar search box (or "+ Add Item" on an empty calendar cell) to open the "New Item" modal.
  2. Pick Main Task or Subtask from the tabs at the top.
  3. Type a title directly, or paste a Figma, Slack thread, Notion, or PR link as-is and its type is detected automatically.
  4. Set a due date to have it reflected on the calendar immediately (you can also leave it empty).

Creating it as a main task immediately adds a new folder to the task tree, and the moment a subtask is attached, Task Manager automatically starts orchestrating it.

How to Use — Subtasks · Worktrees

  1. In the "New Item" modal, choose the Subtask tab, then "Pick a main task…" to target one (you can also create a new main task right there).
  2. Submitting it automatically creates a dedicated git worktree and branch for that subtask. All real code work happens there.

If you already have a worktree (branch) locally and want to bring it in as-is, use the "Connect" button next to any untracked branch in the sidebar's "Worktrees" section — it adopts the branch as a task without creating a new worktree.

How to Use — Notes

Not every subtask needs to belong to a main task. Hit "+" in the sidebar's "Notes" section to create a subtask with no parent — no git worktree, no terminal session, just a name and a description.

Drag notes to reorder them, and click one to open a panel where you can edit its name and description.

How to Use — Task Manager

  • Starts automatically, with no button, the moment a subtask exists.
  • The conductor session is attached directly to the tab's live terminal, so the real conversation happens right there. To direct it yourself, just type into the terminal — there's no separate "send message" box.
  • The "Conversation Log" shows the plan · dispatch · report · message · error trail the conductor keeps for itself, as a structured tree (separate from the raw terminal scroll).

How to Use — Diagram Board

Open "Diagram" on a main task tab to see its subtask chain summarized as cards left-to-right. Each card shows a status dot — waiting, in progress, or session ended — along with its scheduled duration, so you can tell at a glance how far things have gotten.

How to Use — Terminal · Local Server · Browser · Claude Session

Use the "+" at the top of a subtask tab to open any of these panels.

PanelPurpose

Claude SessionA standalone Claude Code session that starts the instant you open the tab, no button needed

A main task tab also lets you open Detail · Task Manager · Diagram · Team Rules from the same "+".

How to Use — Calendar

  1. Open it from the "Calendar" button at the top of the sidebar.
  2. Switch between week and month views to scan your schedule.
  3. Use "+ Add Item" on an empty cell to create a task due on that date right away.
  4. Drag a scheduled item and that subtask's actual due date changes (reflected instantly, exactly like a manual edit).
  5. Use "+ Block Period" in the toolbar to register a reason for a stretch where work shouldn't happen, like a QA freeze — it only shows up as stripes on the calendar and doesn't actually prevent scheduling.

How to Use — Cron Jobs

  1. Open the "Cron Jobs" button at the top of the sidebar, then add a new automation from the list.
  2. Set the automation name and schedule — interval (every N minutes), daily (a time), or weekly (a day of week plus a time).
  3. Set the task title to create and an optional description, and pick a target repo if you have more than one.

At the scheduled time, a new main task is genuinely created automatically. The action is deliberately limited to just "create a new task" — in keeping with the principle that "AI doesn't decide its own scope of work," it only ever runs the schedule a human already set.

How to Use — Model Policy

In the global "Model Policy" tab, pick a model (Fable 5 / Opus 4.8 / Sonnet 4.6, etc.) from a dropdown for each task type — design, Task Manager (subtask chain orchestration), Assistant (calendar · cron jobs · settings), coding, generating QA test cases, and more. A common pattern is a lighter model where speed matters and a stronger one where judgment matters.

How to Use — Team Rules

A main task tab opens with "Team Rules" by default, where you can fill in four free-text fields per repo.

FieldWhen it's used
General rulesAlways included in every agent instruction — commit message format, PR template, etc.
Task-writing rulesStyle and required fields to follow when writing or refining subtasks (e.g. include acceptance criteria)
Worktree · branch creation rulesBranch naming convention. Fill it in and branch names get auto-translated into an English slug
Prerequisites before starting devSteps that must be finished before writing code (e.g. write a Notion spec doc first, then fill in the link)

OpenTask's code never parses the content of this text — it's carried as-is into the agent's instructions, and "following" it is entirely up to the agent, using the shell/MCP tools it already has. Leave all four fields empty and behavior is identical to today.

How to Use — Assistant

The "Assistant" button at the top of the sidebar — opening the tab starts a conversation session immediately, no button needed. Use it to operate the whole app by natural language, not one task — calendar schedule, cron jobs, operational settings.

e.g. "Block next Tuesday through Friday as a QA freeze," "create a cron job that tidies the backlog every morning at 9"

Configuration

You can land on the main screen without connecting a repo — before that, it runs on demo data so you can explore the full layout. There's no mandatory onboarding screen to get past.

Integrations

  • Claude Code CLI — Effectively required. If it isn't installed and logged in locally, agent execution simply won't run (see Requirements above).
  • GitHub — Only needed to monitor PR/CI/issue status (badges, alerts). If gh auth login is already set up locally it's picked up automatically; otherwise you can connect it with one click via OAuth inside the app. Every tab still works without it, just without live GitHub status.
  • Optional — Sentry, AWS, Slack, Notion, Figma. These only power link auto-detection when you paste a URL into a task title — no account is required if you don't have one; just type a plain title instead.

Network

The default bind is 127.0.0.1 (loopback). To open it on the LAN, set OPENRM_HOST=0.0.0.0 — this automatically requires token auth (printed to the console).

Caution. This server can execute git/shell/terminal directly. Don't expose it on an untrusted network.

Security

Designed for local execution. Data is stored on your machine (the packaged app uses the OS standard user-data folder) and never sent to an external server.

Real actions with consequences (a cron job creating a genuine task, injecting into a live agent session) are designed to be visually distinct from mere log information.

Not yet decided. Concurrent multi-user access and permission separation aren't designed yet — it's mid-transition from a single-operator tool to a team tool.

FAQ

Does it support Windows / Linux?

Only macOS builds are provided today. Since it's open source you can try building it for another platform from source, but that isn't officially supported yet.

Can multiple people use it together?

The goal is for a small team to use it together, but concurrent multi-user access and permission separation aren't designed yet.

Does progress get lost if the app (server) restarts?

Orchestrator wave state lives in memory and is lost on restart — a documented v1 limitation. That said, in the packaged app the backend runs as a detached process, so merely closing the app window (including Cmd+Q) doesn't kill a session that's still in progress.

Where is data stored?

On your local machine. The packaged app uses the OS standard user-data folder.

Is it open source?

Yes, released under the MIT license.

Did it have a different name before?

It was rebranded from the internal codename "MRM" → "OpenRM" → "OpenTask" — reflecting a task-centered identity in the name, based on what the top-level unit of work should be.

Can I use it without a GitHub or Notion account?

Yes. GitHub is only needed to monitor PR/CI/issue status — every tab still works without it, just without live GitHub badges. Notion, Figma, and Slack are just link auto-detection conveniences when you paste a URL into a task title, so no account is needed there either. The one real prerequisite is the Claude Code CLI (the claude command) — it must be installed and logged in for agent features like the Task Manager and Claude Session tab to run. If you're already a Claude Code user, it just works with no extra setup.
