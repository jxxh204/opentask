Docs

OpenTask를 설치하고, 각 기능을 실제로 어떻게 쓰는지, 무엇을 조심해야 하는지 정리했습니다.

개요

OpenTask는 태스크 아래 서브태스크를 만들면 각각 격리된 git worktree + AI 코딩 에이전트 (Claude Code 등)가 붙는 병렬 개발 관제탑입니다. 태스크 생성 → 서브태스크(워크트리) → 에이전트 웨이브 → PR 리뷰 → 캘린더 반영까지 이어지는 루프를 GitHub · 터미널 탭을 오가지 않고 한 곳에서 살아있는 상태로 조작하는 것이 목적입니다.

원래는 1인 운영자(오퍼레이터) 도구로 시작했고, 오픈소스로 공개되며 여러 명이 함께 여러 워크트리에서 동시에 도는 에이전트 · PR · 모니터링 신호를 감시하는 소규모 개발팀 대상으로 대상 범위가 넓어졌습니다.

두 가지 실행 형태. ① 소스에서 직접 띄우는 개발 모드(Vite dev server + Node 백엔드가 별도 프로세스), ② 패키징된 macOS Electron 데스크톱 앱. 두 형태 모두 동일한 프론트/백엔드 코드를 쓰며 기능 차이는 없습니다 — Electron은 배포 포맷일 뿐, 별도 기능 세트가 아닙니다. 패키징된 앱은 백엔드를 별도 detached 프로세스로 띄우므로, 앱 창을 완전히 종료해도(Cmd+Q) 진행 중이던 에이전트 세션은 계속 돌아갑니다.

퀵스타트

정식 서명 빌드가 나오기 전까지는 소스에서 3단계로 바로 띄워볼 수 있습니다.

git clone https://github.com/jxxh204/opentask cd opentask/app npm install npm run electron:dev

명령이 끝나면 OpenTask 데스크톱 창이 뜹니다. 아무 설정도 하지 않은 상태라면 데모 데이터로 전체 화면 구조(태스크 트리 · 캘린더 · 크론잡 · 관제)를 바로 둘러볼 수 있습니다. 실제 내 레포에 연결하려면 온보딩 화면에서 "레포 추가"를 누르세요 — 자세한 절차는 설치와 태스크 만들기를 참고하세요.

더 빠르게 보고만 싶다면. npm run electron:dev 대신 npm run start를 실행하면 브라우저에서 http://localhost:5180으로 같은 화면을 볼 수 있습니다(데스크톱 창 없이).

설치

방법 A · 다운로드 앱 (준비 중)

서명 · 공증된 macOS 앱은 현재 준비 중입니다. 공개되면 다운로드 페이지에서 바로 받을 수 있습니다.

방법 B · 소스에서 빌드 (지금 바로 가능)

저장소를 클론하고 app/ 폴더에서 실행합니다.

git clone https://github.com/jxxh204/opentask cd opentask/app npm install npm run start # 백엔드(8770) + 프론트(5180) 동시 실행

데스크톱 창(Electron)으로 바로 띄우고 싶다면:

npm run electron:dev

처음 실행하면 온보딩 화면에서 레포를 연결합니다. 아직 연결하지 않아도 데모 데이터로 화면 구조를 먼저 둘러볼 수 있습니다.

요구 사항

항목내용
Node.js20 이상 (package.json의 engines 기준)
OSmacOS (Electron 데스크톱 앱 기준). 소스는 크로스플랫폼 실행을 막진 않지만 공식 지원은 macOS만
패키지 매니저npm 또는 yarn 둘 다 지원(둘 다 lockfile 존재)

문제 해결 — 네이티브 모듈 빌드 오류

better-sqlite3 · node-pty는 네이티브 모듈이라 Node/Electron 버전이 바뀌면 다시 빌드해야 할 수 있습니다.

# Node용으로 다시 빌드(순수 npm run start / npm run server 용) npm run rebuild:node # Electron용으로 다시 빌드(electron:dev / electron:build 용) npm run electron:rebuild

핵심 개념

태스크와 서브태스크

태스크(메인 태스크, 실제로는 "폴더")는 작업을 묶는 단위입니다. 그 아래 서브태스크를 만들면 각각 격리된 git worktree + 실제 tmux/Claude Code 터미널 세션에 매핑됩니다. 실제 코드 작업은 전부 서브태스크 단위 워크트리에서만 일어나고, 메인 태스크 자신은 오케스트레이션(지휘)만 담당합니다.

태스크 매니저 · 웨이브

태스크 매니저(오케스트레이터)는 별도 "시작" 버튼이 없습니다 — 태스크에 서브태스크가 생기는 순간 자동으로 통제를 시작해, 서브태스크를 순차 "웨이브"로 하나씩 지휘합니다. 라이브 터미널과 함께, 지휘자가 스스로 기록한 계획 · 지시 · 보고 · 메시지 · 오류 로그를 구조화된 트리로 볼 수 있습니다.

v1 제약. 웨이브 진행 상태는 인메모리입니다 — 앱(서버)을 재시작하면 소실됩니다.

다이어그램 (조립 라인 보드)

한 태스크의 서브태스크 체인을 왼쪽 → 오른쪽 조립 라인처럼 요약해서 보여주는 보드입니다. 서브태스크별로 대기 · 진행 중 · 세션 종료 상태와 예정 기간을 카드로 확인할 수 있습니다.

캘린더 · 차단 기간

서브태스크의 예정일을 주/월 단위 캘린더에 배치하고 드래그로 재조정합니다. QA 기간처럼 작업을 진행하면 안 되는 구간은 차단 기간으로 표시해 캘린더에 줄무늬로 남깁니다(실제로 일정 등록을 막지는 않습니다).

팀 규칙

레포마다 다른 개발 관행(브랜치 네이밍, 커밋 포맷, 사전 문서화 요구 등)을 코드에 박지 않고 자유 텍스트로 등록해두면, 그 내용이 그대로 에이전트 지시문에 실려 전달됩니다. OpenTask 코드는 이 텍스트를 파싱하지 않습니다 — "수행"은 그 지시문을 읽는 에이전트가 직접 가진 shell/MCP 툴로 합니다.

모델 배정

설계 · 태스크 매니저 · 관제 · 코딩 · 리뷰 · QA 등 16개 이상의 작업 종류별로 어떤 AI 모델을 쓸지 정책으로 지정합니다.

관제

태스크 하나가 아니라 앱 전체(캘린더 일정 · 크론잡 · 운영 설정)를 대화로 조작하는 최상위 에이전트입니다. 태스크 매니저와 이름 · 자리를 분리해, "이 태스크"가 아니라 "이 앱 전체"를 지휘합니다.

살아있는 연결 — PR 리뷰

PR 리뷰 코멘트에 리뷰 적용을 누르면 해당 서브태스크의 살아있는 터미널 세션에 실제 지시가 주입되고, 커밋 · 푸시까지 진행됩니다. 리뷰 항의를 누르면 실제 GitHub에 공개 답글이 게시됩니다.

되돌릴 수 없는 액션. 위 두 동작은 로그성 정보가 아니라 실제로 되돌릴 수 없는 액션입니다. OpenTask는 이런 액션을 시각적으로 명확히 구분해 보여줍니다.

사용 방법 — 태스크 만들기

  1. 사이드바 검색창 위 "태스크 추가"(또는 캘린더 빈 칸의 "+ 작업 추가")를 누르면 "일감 생성" 모달이 열립니다.
  2. 상단 탭에서 메인 태스크 / 서브태스크를 고릅니다.
  3. 제목 칸에 직접 타이핑하거나, Figma · 슬랙 스레드 · Notion · PR 링크를 그대로 붙여넣으면 자동으로 종류가 인식됩니다.
  4. 예정일을 지정하면 캘린더에도 곧바로 반영됩니다(비워둘 수도 있음).

메인 태스크로 생성하면 그 순간 태스크 트리에 새 폴더가 생기고, 서브태스크가 붙는 즉시 태스크 매니저가 자동으로 오케스트레이션을 시작합니다.

사용 방법 — 서브태스크 · 워크트리

  1. "일감 생성" 모달에서 서브태스크 탭 선택 → "메인 태스크 고르기…"로 대상 메인 태스크를 지정합니다(그 자리에서 새 메인 태스크를 만들 수도 있습니다).
  2. 제출하면 그 서브태스크 전용 git worktree + 브랜치가 자동으로 만들어집니다. 실제 코드 작업은 여기서만 일어납니다.

이미 로컬에 만들어둔 워크트리(브랜치)를 그대로 가져오고 싶다면, 사이드바 "워크트리" 섹션에서 아직 태스크로 등록되지 않은 브랜치 옆 "연결" 버튼을 누르면 새 워크트리를 만들지 않고 그 브랜치를 그대로 태스크로 편입합니다.

사용 방법 — 태스크 매니저

  • 서브태스크가 생기는 순간 별도 버튼 없이 자동으로 시작됩니다.
  • 탭 본문의 라이브 터미널에 지휘자(conductor) 세션이 그대로 붙어 있어, 실제 대화가 여기서 오갑니다. 직접 지시하고 싶으면 터미널에 바로 타이핑하면 됩니다 — 별도 "메시지 보내기" 입력창은 없습니다.
  • "대화 로그"에서는 지휘자가 스스로 기록한 계획 · 지시 · 보고 · 메시지 · 오류를 구조화된 트리로 볼 수 있습니다(raw 터미널 스크롤과 별개).

사용 방법 — 다이어그램 보드

메인 태스크 탭에서 "다이어그램"을 열면, 그 태스크의 서브태스크 체인을 왼쪽 → 오른쪽 카드로 요약해서 보여줍니다. 카드마다 대기 · 진행 중 · 세션 종료 상태 점과 예정 기간이 표시되어, 지금 뭐가 어디까지 됐는지 한눈에 파악할 수 있습니다.

사용 방법 — 터미널 · 로컬 서버 · 브라우저 · 클로드 세션

서브태스크 탭 상단의 "+"로 아래 패널들을 추가로 열 수 있습니다.

패널용도
터미널그 워크트리의 실제 tmux + node-pty 터미널. 여러 개 동시에 열어 여러 에이전트를 병행 조작 가능
로컬 서버워크트리의 dev 서버를 바로 실행해 확인
브라우저임베디드 브라우저로 실행 결과를 새 창 없이 미리보기
클로드 세션버튼 없이 탭을 열면 바로 시작되는 독립 Claude Code 세션

메인 태스크 탭에는 추가로 상세 · 태스크 매니저 · 다이어그램 · 팀 규칙도 같은 "+"로 열 수 있습니다.

사용 방법 — 캘린더

  1. 사이드바 상단 "캘린더" 버튼으로 엽니다.
  2. 주/월 보기를 전환하며 일정을 훑어봅니다.
  3. 빈 칸의 "+ 작업 추가"로 그 날짜를 예정일로 하는 태스크를 바로 만들 수 있습니다.
  4. 일정 카드를 드래그하면 그 서브태스크의 실제 예정일이 바뀝니다(수동 입력과 동일하게 즉시 반영).
  5. 툴바의 "+ 일정 막기"로 QA 기간처럼 작업하면 안 되는 구간에 이유를 적어 등록합니다 — 캘린더에 줄무늬로 표시될 뿐, 실제 일정 등록 자체를 막지는 않습니다.

사용 방법 — PR 리뷰

  1. 사이드바 태스크 행의 배지를 확인합니다 — 처리할 리뷰가 있으면 "이슈 N", 없으면 "리뷰 완료"로 표시됩니다.
  2. 배지를 클릭하면 PR 리뷰 모달이 열립니다.
  3. 코멘트별로 리뷰 적용(해당 서브태스크의 살아있는 세션에 지시를 주입 — 확인 후 실제로 커밋 · 푸시까지 진행) 또는 리뷰 항의(왜 맞지 않는지 사유를 적으면 그대로 GitHub에 공개 답글로 게시)를 선택합니다.

사용 방법 — 크론잡

  1. 사이드바 상단 "크론잡" 버튼 → 목록에서 새 자동화를 추가합니다.
  2. 자동화 이름과 주기를 정합니다 — 반복 간격(N분마다), 매일(시:분), 매주(요일 + 시:분) 중 하나.
  3. 생성할 일감 제목과 설명(선택), 레포가 여럿이면 대상 레포를 지정합니다.

정해진 시각이 되면 실제로 새 메인 태스크가 자동 생성됩니다. 액션은 "새 일감 생성" 하나로 의도적으로 제한되어 있습니다 — "AI가 스스로 작업 범위를 정하지 않는다"는 원칙에 따라, 사람이 미리 정한 스케줄만 그대로 실행합니다.

사용 방법 — 모델 배정

전역 탭 "모델 배정"에서, 설계 · 태스크 매니저(서브태스크 체인 조율) · 관제(캘린더 · 크론잡 · 설정) · 코딩 · PR 리뷰 · 리뷰 반영 · QA 테스트케이스 생성 등 작업 종류마다 드롭다운으로 사용할 모델(Fable 5 / Opus 4.8 / Sonnet 4.6 등)을 지정합니다. 속도가 중요한 작업엔 가벼운 모델을, 판단이 중요한 작업엔 상위 모델을 배정하는 식으로 씁니다.

사용 방법 — 팀 규칙

메인 태스크 탭을 열면 기본으로 함께 열리는 "팀 규칙"에서 레포당 자유 텍스트 4칸을 채울 수 있습니다.

칸언제 쓰이나
일반 규칙모든 에이전트 지시문에 항상 함께 실림 — 커밋 메시지 포맷, PR 템플릿 등
태스크 작성 규칙서브태스크를 쓰거나 다듬을 때 참고할 문체 · 필수 항목(예: 완료 기준 포함)
워크트리 · 브랜치 생성 규칙브랜치 네이밍 컨벤션. 채우면 브랜치명이 자동으로 영문 슬러그로 번역됨
개발 시작 전 필수 조건코드 작성 전에 먼저 끝내야 할 절차(예: 노션 스펙 문서 작성 후 링크 채우기)

OpenTask 코드는 이 텍스트의 내용을 파싱하지 않습니다 — 그대로 에이전트 지시문에 얹혀 전달되고, 실제 "수행"은 그 지시문을 읽는 에이전트가 이미 가진 shell/MCP 툴로 합니다. 네 칸을 전부 비워두면 지금과 완전히 동일하게 동작합니다.

사용 방법 — 관제

사이드바 상단 "관제" 버튼 — 탭을 열면 버튼 없이 바로 대화 세션이 시작됩니다. 특정 태스크가 아니라 앱 전체(캘린더 일정 · 크론잡 · 운영 설정)를 자연어로 조작할 때 씁니다.

예: "다음 주 화요일부터 금요일까지 QA 기간으로 막아줘", "매일 아침 9시에 백로그 정리하는 크론잡 만들어줘"

기능 요약

대상 레포에 연결하면 아래 탭들이 워크스페이스 안에서 열립니다. 각 항목의 실제 사용법은 위 "사용 방법"을 참고하세요.

탭하는 일
태스크 매니저서브태스크가 생기면 자동으로 시작되는 AI 지휘자. 순차 웨이브 실행 + 라이브 터미널 + 계획/지시/보고 로그
다이어그램서브태스크 체인을 조립 라인처럼 요약한 보드 — 상태(대기/진행/종료)와 예정 기간
상세태스크(폴더) 상세 — 기간 · 설명 · 개발 계획, AI 제안 적용
서브태스크서브태스크 개별 상세 패널
터미널서브태스크 워크트리의 실제 tmux + node-pty 터미널
로컬 서버워크트리의 dev 서버를 바로 띄워 확인
브라우저임베디드 브라우저로 실행 결과 미리보기
클로드 세션버튼 없이 탭을 열면 바로 시작되는 즉석 Claude Code 세션
팀 규칙레포당 자유 텍스트 4칸으로 에이전트 지시문에 실릴 팀 규칙 정의
크론잡N분마다 · 매일 · 매주 예약 — 액션은 "새 일감 생성"으로 의도적으로 제한
모델 배정설계 · 태스크 매니저 · 코딩 · 리뷰 · QA 등 작업 종류별 AI 모델 정책
캘린더서브태스크 일정을 주/월 단위로 배치 · 드래그 재조정, 차단 기간 표시
관제태스크 하나가 아니라 앱 전체(캘린더 · 크론잡 · 설정)를 대화로 조작

PR 리뷰

태스크/서브태스크에 연결된 PR에 리뷰 코멘트가 달리면 사이드바 배지로 알려주고, 모달에서 코멘트별로 리뷰 적용(커밋 · 푸시까지 진행) 또는 리뷰 항의 (GitHub에 공개 답글)를 선택할 수 있습니다.

설정

초기 설정(Setup)을 마치기 전에는 메인 화면 전체가 게이팅되어 접근할 수 없습니다. 설정 전에는 데모 데이터로 동작합니다.

연동

  • 필수 — GitHub (PR/이슈/CI 상태를 읽고, 필요 시 코멘트를 게시)
  • 선택 — Sentry, AWS, Slack, Notion, Figma. 필요한 것만 연결하면 됩니다.

네트워크

기본 바인딩은 127.0.0.1(loopback)입니다. LAN에 열려면 OPENRM_HOST=0.0.0.0으로 설정하고, 이 경우 토큰 인증이 자동으로 요구됩니다 (콘솔에 출력).

주의. git/셸/터미널을 직접 실행할 수 있는 서버입니다. 신뢰할 수 없는 네트워크에는 노출하지 마세요.

보안

로컬 실행을 전제로 설계되었습니다. 데이터는 내 컴퓨터에 저장되며(패키징 앱은 OS 표준 사용자 데이터 폴더), 외부 서버로 전송되지 않습니다.

되돌릴 수 없는 실제 액션(GitHub 공개 게시, 살아있는 세션에 지시 주입)은 일반 로그성 정보와 시각적으로 명확히 구분되도록 설계되어 있습니다.

미확정 영역. 다중 사용자 동시 접근/권한 분리는 아직 설계되지 않았습니다 — 1인 운영자 도구에서 팀 도구로 확장 중인 과도기입니다.

FAQ

Windows / Linux도 지원하나요?

현재는 macOS 빌드만 제공합니다. 오픈소스이므로 소스에서 직접 다른 플랫폼용으로 빌드를 시도해볼 수는 있지만, 공식 지원 대상은 아직 아닙니다.

여러 명이 같이 쓸 수 있나요?

소규모 팀이 함께 쓰는 것을 목표로 하지만, 다중 사용자 동시 접근/권한 분리는 아직 설계되지 않았습니다.

앱(서버)을 재시작하면 진행 상태가 사라지나요?

오케스트레이터 웨이브 상태는 인메모리라 재시작 시 소실됩니다 — v1 범위로 명시된 제약입니다. 다만 패키징된 앱은 백엔드가 detached 프로세스로 분리돼 있어, 앱 창만 닫는 것으로는(Cmd+Q 포함) 진행 중이던 세션이 죽지 않습니다.

데이터는 어디에 저장되나요?

로컬 컴퓨터에 저장됩니다. 패키징된 앱은 OS 표준 사용자 데이터 폴더를 사용합니다.

오픈소스인가요?

네, MIT 라이선스로 공개되어 있습니다.

이전 이름이 있었나요?

내부 코드네임 "MRM" → "OpenRM"을 거쳐 "OpenTask"로 리브랜딩했습니다 — 무엇을 최상위 단위로 삼는가를 기준으로 태스크 중심 정체성을 이름에 반영했습니다.
