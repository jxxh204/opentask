# Product

## Platform

web

## Users

개발자 · 소규모 개발팀 운영자. GitHub 또는 입소문으로 OpenTask를 처음 접하고, 설치(다운로드)할지 결정하는 평가 단계의 방문자가 핵심 대상이다. 앱 자체의 실사용자(오퍼레이터)와는 다른 역할 — 방문자는 아직 도구를 쓰기 전, "이게 내 문제를 해결하는가 / 신뢰할 만한가"를 판단 중이다.

## Product Purpose

방문자가 OpenTask를 "실제로 써볼 가치가 있는 도구"로 판단해 다운로드하거나(또는 소스 빌드) GitHub에서 더 탐색하도록 설득하는 것. 부차적으로 기존 사용자를 위한 Docs·릴리스 노트 레퍼런스 역할도 한다.

## Positioning

**핵심 추상화 단위는 "태스크"다 — 터미널도, Claude 세션도 아니다.** (2026-08-30, 제작자 직접 정정) 사용자에게는 처리해야 할 일(태스크)이 있을 뿐이다. 그 태스크를 실제로 처리하려면 워크트리(격리된 리소스 공간)·브랜치·Claude 세션·터미널이 필요하지만, 이건 전부 태스크 입장에서는 세부사항이다. OpenTask는 이 세부사항(인프라 프로비저닝·에이전트 구동·진행 추적)을 도구가 대신 운용하게 만들어서, 사람은 "할 일 목록"만 다루면 되게 하려고 만든 도구다. 즉 "여러 터미널/에이전트 세션을 지켜보는 관제 도구"가 아니라 "태스크를 맡기면 그 아래 워크트리·브랜치·에이전트·터미널을 도구가 알아서 프로비저닝하고 굴리는 태스크 관리 도구"다 — 터미널·세션은 결과물이 흘러나오는 창일 뿐, 사용자가 사고하는 단위가 아니다.

앱 자체의 포지셔닝(로그만 보여주는 대시보드가 아니라 실제 git worktree·Claude 세션·GitHub API에 물린 살아있는 제어판)은 여전히 유효하다 — 다만 "무엇을 살아있게 제어하는가"의 단위가 터미널이 아니라 태스크라는 게 핵심 정정이다. "리뷰에 적용을 누르면 실제로 커밋된다"는 식의 주장은 과장이 아니라 실제 화면·코드로 뒷받침되는 사실이어야 한다.

**왜 만들었는가(방문자에게 설명해야 할 문제).** 여러 git worktree·브랜치·AI 코딩 세션을 병렬로 굴리기 시작하면, 정작 힘든 건 코딩이 아니라 "이 워크트리가 무슨 일 때문에 떠 있었더라", "이 터미널이 어느 태스크였지" 같은 인프라-단위 추적이 된다 — PR은 GitHub에, 대화는 각 터미널에, 진행 상황은 사람 머릿속에만 있다. OpenTask는 이 문제를 "인프라를 태스크 아래로 숨긴다"로 푼다 — 사람은 태스크만 만들고 관리하면, 워크트리·브랜치·세션·터미널은 도구가 알아서 그 태스크에 매달아 운용한다. 원래 1인 운영자가 자기 자신을 위해 만든 도구다(오케스트레이션 프롬프트에 "마티"라는 이름이 기본 오퍼레이터로 하드코딩돼 있던 것이 그 증거). 오픈소스로 공개되며 비슷한 문제를 겪는 소규모 팀 대상으로 넓어졌다. 리디자인된 홈페이지는 이 "왜"를 방문자가 바로 알아볼 수 있게 명시적으로 설명해야 한다 — "터미널을 여러 개 지켜본다"가 아니라 "할 일을 적으면 나머지(워크트리/브랜치/세션)는 신경 안 써도 된다"는 프레이밍으로.

## Operating Context

- 정적 사이트(Vite 빌드, HTML/CSS + 약간의 JS) — 모노레포 안 `website/` 서브프로젝트. `app/`(Electron 데스크톱 앱)와는 별개 코드베이스이자 별개 방문자층.
- 영어가 기본(루트 도메인) — 오픈소스 프로젝트라 글로벌 GitHub 방문자가 1차 대상. 한국어는 `/ko/` 경로로 병행 제공. 콘텐츠는 항상 두 언어 동시에 갱신한다. (2026-08-30: 기존엔 한국어가 루트였으나 방문자 우선순위를 영어로 전환 — `index.html`↔`en/`을 `index.html`↔`ko/`로 실제 교체 완료.)
- 다운로드/변경 이력/Docs 페이지도 동일 구조: `download.html`·`docs.html`·`changelog.html`(영어, 루트) / `ko/download.html`·`ko/docs.html`·`ko/changelog.html`(한국어).
- Cloudflare Workers(Direct Upload, `npx wrangler deploy`)에 배포, 커스텀 도메인 `opentask.jaehwankim.dev`에서 서비스. Vercel(`opentask-website.vercel.app`)은 2026-08-30부로 롤백용으로만 남겨두고 더는 배포 대상이 아님 — 자세한 경위는 `CLOUDFLARE_MIGRATION.md` 참고.
- 실제 앱 다운로드는 GitHub Releases(`jxxh204/opentask`) 자산으로 링크 — 웹사이트가 파일을 직접 호스팅하지 않는다.
- 페이지 구성: 랜딩(index.html) · Docs(docs.html) · 다운로드(download.html) · 릴리스 노트(changelog.html), 각 한/영.

## Capabilities and Constraints

- Docs 페이지에 실제 앱 화면 스크린샷 7장이 포함되어 있다(퀵스타트 모달, 일감 생성, 개요, 캘린더, 크론잡 생성, 설정, 모델 배정) — 데모 데이터만 사용, 실제 회사/고객 정보 없음.
- 미확정/미보유: 태스크 매니저 · PR 리뷰 · 비서(Assistant) 탭의 스크린샷은 아직 없다. 해당 탭들은 여는 순간 실제 git worktree + 유료 Claude Code 에이전트를 구동하는 부작용이 있어(§app 코드), 안전한 캡처 방법이 확정되기 전까지 보류 중이다.
- 가짜 고객·테스트모니얼·벤치마크·로고는 만들지 않는다 — 실제 사내 도구를 추출해 공개한 오픈소스 릴리스라는 배경에서 나온 제약이며, 앞으로도 유지되어야 한다.
- 실사용자 후기, GitHub 스타 수, 채택 지표 등 사회적 증거는 현재 없음 — 생기기 전까지는 없는 채로 두는 편이 정직성 원칙에 맞는다.

## Brand Commitments

- 제품명 OpenTask, 저장소 `jxxh204/opentask`, MIT 라이선스.
- 시맨틱 컬러 규칙(blue=PR·링크, green=진행·성공, amber=대기·주의, red=실패·삭제)은 앱 디자인 시스템과 공유 — 웹사이트의 "Design" 섹션이 이 규칙 자체를 방문자에게 설명하는 콘텐츠이기도 하다.
- 영어가 기본 카피 언어(위 Operating Context 참고), 한국어 병행. Pretendard 계열 폰트(한글 지원 필요).

## Evidence on Hand

- 실제 공개 GitHub 저장소(MIT), 실제 서명된 macOS 릴리스(Apple Developer ID 서명 완료, 공증은 아직).
- Docs의 스크린샷 7장(`website/public/screenshots/`) — 모두 clean 데모 데이터에서 캡처.
- 코드베이스(`app/src`, `app/server`)와 `app/README.md` 등 문서가 기능 설명의 근거.
- 없음, 꾸며내지 않을 것: 실사용자 후기, 채택 지표, 데모 영상/GIF, 위에 명시된 3개 탭의 스크린샷.

## Product Principles

1. 웹사이트의 모든 주장은 실제 코드·화면으로 검증 가능해야 한다 — 앱의 "살아있는 연결" 포지셔닝을 과장 없이 그대로 증명한다.
2. 개인 오픈소스 프로젝트의 정직성을 우선한다 — 가짜 고객·지표·후기를 만들지 않고, 증거가 없으면 없다고 그대로 둔다.
3. 방문자는 아직 설치하지 않은 평가자다 — 카피와 구조는 "이게 뭘 하는지"와 "왜 다른지"에 가장 먼저 답해야 한다. "터미널/에이전트를 감시한다"가 아니라 "태스크를 맡기면 인프라(워크트리·브랜치·세션)는 신경 안 써도 된다"가 1순위 메시지다.
4. 한/영 두 언어는 항상 동시에 갱신한다 — 한쪽만 바뀐 상태로 배포하지 않는다.
5. 화면 스크린샷은 안전하게 확보 가능한 데모 데이터로만 캡처한다 — 실제 에이전트를 구동시키는 화면(태스크 매니저·PR 리뷰·비서)은 부작용 통제 방법이 없는 한 캡처하지 않는다.
